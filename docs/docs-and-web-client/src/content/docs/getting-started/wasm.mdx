Lipi Lekhika includes a blazing-fast 🦀 **Rust-based WebAssembly (WASM) module** that brings high-performance transliteration to all JavaScript environments. The WASM implementation provides significant performance improvements while maintaining the same easy-to-use API.

## Features

The WASM module offers several advantages over the pure JavaScript implementation:

- **⚡ Superior Performance** — Rust's compiled WASM code executes significantly faster than JavaScript
- **📦 Compact Size** — Only 114 KB gzipped (base64), or 80 KB as a `.wasm` file, including all script data embedded
- **🌍 Universal Compatibility** — Works with no setup in Node.js, Bun, Deno and browsers (any bundler), and on Cloudflare Workers and Vercel Edge through [`lipilekhika/wasm`](#cloudflare-workers-and-edge-runtimes)
- **🔒 Type Safety** — Built with Rust's type system for reliability
- **🎯 Same API** — Drop-in replacement for the standard `transliterate` function

## Basic Usage

### Simple Transliteration

The `transliterate_wasm` function provides the same interface as `transliterate` (`text`: `string | string[]`):

```typescript
import { transliterate_wasm } from 'lipilekhika';

const result = await transliterate_wasm('na jAyatE mriyatE vA', 'Normal', 'Devanagari');
console.log(result); // न जायते म्रियते वा
```

### With Custom Options

You can pass custom transliteration options just like the standard function:

```typescript
import { transliterate_wasm } from 'lipilekhika';

const result = await transliterate_wasm(
  'गङ्गा',
  'Devanagari',
  'Gujarati',
  { 'brahmic_to_brahmic:replace_pancham_varga_varna_with_anusvAra': true }
);
console.log(result); // ગંગા (instead of ગઙ્ગા)
```

## Preloading the WASM Module

To avoid the initial loading delay when first calling `transliterate_wasm`, you can preload the WASM module:

```typescript
import { preloadWasm, transliterate_wasm } from 'lipilekhika';

// Preload during app initialization
await preloadWasm();

// Later calls will be instant (no loading delay)
const result = await transliterate_wasm('namaste', 'Normal', 'Devanagari');
console.log(result); // नमस्ते
```

<Aside type="tip">
  **Best Practice**: Call `preloadWasm()` during your application's initialization phase (e.g., in a loader, startup hook, or top-level await) to ensure the WASM module is ready before users interact with transliteration features.
</Aside>

## Choosing an Entry Point

The same `transliterate_wasm` is available from three entry points. They differ only in how the WASM module is loaded.

| Import | How the WASM is loaded | Use it for |
| --- | --- | --- |
| `lipilekhika` | Embedded (base64) in a lazily loaded chunk | **Recommended.** Node.js, Bun, Deno, browsers, every bundler and CDN, with no setup |
| `lipilekhika/wasm` | Picked by the runtime: the `.wasm` file is imported as a module on Cloudflare Workers (`workerd`) and Vercel Edge (`edge-light`), fetched as a separate file in browsers (with the embedded module as fallback), embedded in Node.js, Bun and Deno | Cloudflare Workers and Vercel Edge (required there), code shared between such a server and the browser, and browsers when you want the separate `.wasm` file |
| `lipilekhika/wasm/slim` | Nothing embedded: you pass the `.wasm` file (`lipilekhika/lipilekhika.wasm`) to `initWasm()` | A strict Content Security Policy, serving the `.wasm` yourself (CDN, cache), or a runtime not covered above |

<Aside type="tip">
  **Use `transliterate_wasm` from `lipilekhika` unless your server code runs on Cloudflare Workers or Vercel Edge.** It needs no bundler configuration and no asset handling, and the WASM chunk is only loaded when `transliterate_wasm` or `preloadWasm` is first called, so it does not add to your initial bundle.
</Aside>

## Cloudflare Workers and Edge Runtimes

Cloudflare Workers and the Vercel Edge runtime do not allow compiling WebAssembly from bytes at runtime: a `.wasm` file has to be imported as a module. The embedded module of `lipilekhika` can not load there, its `transliterate_wasm` throws an error pointing to `lipilekhika/wasm`.

Import from `lipilekhika/wasm` instead. It has the same API (`transliterate_wasm`, `preloadWasm`), and the Worker ships the `.wasm` file (80 KB gzipped) as a WebAssembly module:

```typescript
import { transliterate_wasm } from 'lipilekhika/wasm';

export default {
  async fetch() {
    const text = await transliterate_wasm('namaskAra', 'Normal', 'Devanagari');
    return new Response(text); // नमस्कार
  }
};
```

The package's export conditions pick the right build, so no configuration is needed:

- **Cloudflare Workers** (`workerd` condition) — `wrangler`, the Cloudflare Vite plugin and frameworks using it (Astro, SvelteKit, React Router, Nuxt, TanStack Start on Cloudflare, ...) import the `.wasm` file as a `WebAssembly.Module`, in `dev` and in the deployed Worker.
- **Vercel Edge / Next.js edge runtime** (`edge-light` condition) — the `.wasm` file is imported with the `?module` suffix.
- **Browsers** (`browser` condition) — the `.wasm` file is fetched (see [In the Browser](#in-the-browser)).
- **Everywhere else** (Node.js, Bun, Deno) — the embedded module, the same as `lipilekhika`.

So in a full stack app (eg. Astro on Cloudflare) the same `import { transliterate_wasm } from 'lipilekhika/wasm'` works in server code running on the Worker and in client code running in the browser.

### In the Browser

In browsers `lipilekhika/wasm` fetches the `.wasm` file from `new URL('../lipilekhika.wasm', import.meta.url)`: it is downloaded and cached as its own file (80 KB gzipped, against 114 KB for the base64 copy in JavaScript) and compiled while it streams. Bundlers that handle this pattern emit the file as an asset; without a bundler (a CDN `import`) it is fetched as is.

If the file can not be loaded, `lipilekhika/wasm` falls back to the embedded module (a separate chunk, only downloaded in that case) and logs a warning:

| Setup | Extra config |
| --- | --- |
| Vite 8 (Astro 7, SvelteKit, ...) — dev and build | None |
| Vite 7 and older — build | None |
| Vite 7 and older — dev | The dependency pre-bundling moves the module away from the file: add `optimizeDeps: { exclude: ['lipilekhika'] }` to load the file (without it the embedded module is used) |
| esbuild (`--bundle`) | esbuild leaves the URL as is: copy `node_modules/lipilekhika/dist/lipilekhika.wasm` to the folder above your bundle, or use `lipilekhika/wasm/slim` (without it the embedded module is used) |

```js
// vite.config.js (Vite 7 and older)
export default {
  optimizeDeps: { exclude: ['lipilekhika'] }
};
```

<Aside type="note">
  `lipilekhika/wasm` can be used in every environment, but its `.wasm` import only works with the tooling of those runtimes, so it is offered as a separate entry point and `lipilekhika` stays usable with any bundler.
</Aside>

## Manual Initialization (`lipilekhika/wasm/slim`)

`lipilekhika/wasm/slim` embeds nothing: call `initWasm()` once with the `.wasm` file, which the package exports as `lipilekhika/lipilekhika.wasm`. It accepts a `WebAssembly.Module`, the bytes, a `Response` (or a promise of one), or a URL to fetch.

<Tabs>
  <TabItem label="Vite (browser)">
    ```typescript
    import { initWasm, transliterate_wasm } from 'lipilekhika/wasm/slim';
    // the `.wasm` file is emitted as an asset and fetched (and compiled) while streaming
    import wasmUrl from 'lipilekhika/lipilekhika.wasm?url';

    await initWasm(wasmUrl);
    const result = await transliterate_wasm('namaste', 'Normal', 'Devanagari');
    ```
  </TabItem>
  <TabItem label="Cloudflare Workers">
    ```typescript
    import { initWasm, transliterate_wasm } from 'lipilekhika/wasm/slim';
    import wasmModule from 'lipilekhika/lipilekhika.wasm'; // a WebAssembly.Module

    await initWasm(wasmModule);
    ```
  </TabItem>
  <TabItem label="Vercel Edge">
    ```typescript
    import { initWasm, transliterate_wasm } from 'lipilekhika/wasm/slim';
    import wasmModule from 'lipilekhika/lipilekhika.wasm?module'; // a WebAssembly.Module

    await initWasm(wasmModule);
    ```
  </TabItem>
  <TabItem label="CDN">
    ```typescript
    import { initWasm, transliterate_wasm } from 'lipilekhika/wasm/slim';

    // use the same version as the installed package: the `.wasm` file and the JS must match
    await initWasm(fetch('https://cdn.jsdelivr.net/npm/lipilekhika@1.0.14/dist/lipilekhika.wasm'));
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```typescript
    import { readFile } from 'node:fs/promises';
    import { createRequire } from 'node:module';
    import { initWasm, transliterate_wasm } from 'lipilekhika/wasm/slim';

    const require = createRequire(import.meta.url);
    await initWasm(await readFile(require.resolve('lipilekhika/lipilekhika.wasm')));
    ```
  </TabItem>
</Tabs>

`lipilekhika/wasm/slim` does not make the module smaller: it is the same `.wasm` file that `lipilekhika/wasm` loads on its own in browsers, on Workers and on Vercel Edge. Use it when you want to decide where the file comes from.

<Aside type="note">
  All entries (`lipilekhika`, `lipilekhika/wasm`, `lipilekhika/wasm/slim`) share one WASM instance: the first one used loads the module, the others then use it. If the module is already loaded, `initWasm()` resolves without loading anything.
</Aside>

<Aside type="caution">
  **Content Security Policy:** compiling WebAssembly in a browser needs `'wasm-unsafe-eval'` in `script-src`, whichever entry you use. `lipilekhika/wasm` and `lipilekhika/wasm/slim` also fetch the `.wasm` file, which `connect-src` must allow (your own origin, or the CDN).
</Aside>

## API Reference

### `transliterate_wasm(text, from, to, options?)`

WASM-based transliteration using the Rust implementation.

**Parameters:**
- `text: string | string[]` — One string or many (same options for all)
- `from: ScriptLangType` — Source script/language name
- `to: ScriptLangType` — Target script/language name
- `options?: TransliterationOptions` — Optional custom transliteration options

**Returns:** `Promise<string | string[]>` — shape matches `text`

**Example:**
```typescript
const result = await transliterate_wasm('hello', 'Normal', 'Telugu');
console.log(result); // హెల్లొ
```

### `preloadWasm()`

Preloads the WASM module to eliminate initial loading delay.

**Returns:** `Promise<void>`

**Example:**
```typescript
// During app initialization
await preloadWasm();

// Now WASM calls are instant
const result = await transliterate_wasm('text', 'Normal', 'Devanagari');
```

### `initWasm(wasm)` (`lipilekhika/wasm/slim`)

Initializes the WASM module of `lipilekhika/wasm/slim`. Call it before `transliterate_wasm` (from `lipilekhika/wasm/slim`); calling it again returns the same initialization. If it fails (eg. the fetch of the file), it can be called again.

**Parameters:**
- `wasm: WasmSource` — A `WebAssembly.Module`, the bytes (`BufferSource`), a `Response`, a URL (`string | URL`) to fetch, or a promise of one of these

**Returns:** `Promise<void>`

## Performance Comparison

The WASM implementation provides significant performance improvements, especially for:

- **Large text blocks** — Faster processing of lengthy documents
- **Batch operations** — Efficient when transliterating multiple texts
- **Complex scripts** — Better performance with intricate character mappings
- **Repeated calls** — Lower overhead after initial load
- **Benchmarks** - 2x faster than the JavaScript implementation

<Aside type="note">
  For small, one-off transliterations, the performance difference may be negligible due to WASM initialization overhead. The WASM module shines with repeated use or larger text processing.
</Aside>

## When to Use WASM vs JavaScript

**Use WASM (`transliterate_wasm`) when:**
- Processing large volumes of text
- Performance is critical
- You're making repeated transliteration calls
- Building production applications

**Use JavaScript (`transliterate`) when:**
- Making occasional, small transliterations
- Bundle size is extremely constrained
- You need maximum compatibility with older environments
- Debugging or development (easier stack traces)

## Bundle Size

The WASM module adds only **114 KB (gzipped base64)** to your bundle, or **80 KB (gzipped)** as the `.wasm` file used by `lipilekhika/wasm` on Workers / Edge and by `lipilekhika/wasm/slim`. It includes:
- The compiled Rust WASM binary
- All script data embedded (no external data files needed)
- Complete transliteration logic

This is remarkably compact considering it includes all the data and logic for 15+ scripts!

## Technical Details

### How It Works

1. The WASM module is compiled from the Rust implementation of Lipi Lekhika
2. All script data is embedded directly into the WASM binary at compile time
3. The module is lazy-loaded on first use (or via `preloadWasm()`)
4. Subsequent calls reuse the loaded module for optimal performance

The `.wasm` binary is embedded as base64 in `lipilekhika`, so no bundler or server has to handle a `.wasm` file. It is also shipped as a file (`lipilekhika/lipilekhika.wasm`), which `lipilekhika/wasm` imports as a module on Cloudflare Workers / Vercel Edge and which `lipilekhika/wasm/slim` takes from you.

### Browser Compatibility

The WASM module requires WebAssembly support, which is available in:
- Chrome/Edge 57+
- Firefox 52+
- Safari 11+
- Node.js 8+
- Deno (all versions)
- Bun (all versions)

<Aside type="caution">
  Very old browsers (IE11, old mobile browsers) do not support WebAssembly. For maximum compatibility, fall back to the standard `transliterate` function or use feature detection.
</Aside>
